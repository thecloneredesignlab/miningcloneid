What the ploidyOxygen workflow already does
- Reconstructs 2N and 4N lineage histories across passages and oxygen changes.
- Associates each passage with:
  - observed growth rate when available
  - binned flow cytometry when available
  - reassigned karyotype summaries when available
- Serializes lineage-aware simulation jobs:
  - jobs_2N.Rds
  - jobs_4N.Rds
- Encodes the in vitro oxygen history explicitly as passage-to-passage trajectories, rather than as a small set of independent conditions.

Interpretation of the current exercise
- The intended scientific direction is no longer the old coarse DEoptim workflow.
- The intended target is the MAP oxygen supply-demand model.
- The available in vitro data assembly still lives in ploidyOxygen and remains a distinct upstream data-preparation layer.
- The bridge from those in vitro fit objects into the MAP simulation/objective code now exists, but it is still an exploratory first-pass workflow rather than a finalized fitter.
- The project is therefore currently split across:
  - model/fitter infrastructure in oxygen/code/O2_supply_demand_MAP
  - in vitro adapter/objective/report code in oxygen/code/in-vitro-utils and oxygen/workflow
  - upstream lineage data engineering in oxygen/ploidyOxygen

Main remaining gap
- The codebase now supports an end-to-end in vitro objective and diagnostic workflow, but the scientific/objective design is still provisional.
- The main open work is no longer “build the bridge”; it is to decide which simplifications to keep, which observables to fit, and whether to fold this workflow into a more formal fitter entry point later.

Likely near-term tasks
- Evaluate the current checkpoint fit and decide whether the objective should stay at:
  - growth plus mean-ploidy summary errors
  - lineage-level sequential ploidy fits with the current passage approximation
  - or a richer flow/karyotype-based likelihood later
- Revisit current in vitro simplifications:
  - pooled lineage/cohort cell-count targets
  - fixed-O2 passage handling
  - short sampled-start local optimization rather than a larger global search
- Decide whether the current workflow should remain as standalone exploratory scripts/reporting or be promoted into a more formal fitter interface.

Current status summary
- Data side: partially prepared for in vitro lineage fitting in ploidyOxygen.
- Model side: newer MAP oxygen supply-demand model exists and is likely the correct target.
- Integration side: a first end-to-end in vitro adapter/objective workflow now exists under oxygen/code/in-vitro-utils and oxygen/workflow, with a committed checkpoint parameter snapshot for report fallback.
- Current in vitro chromosome-count semantics:
  - `ploidyOxygen/data/fit_objects/fit_data.Rds` now stores `kary` as total chromosome count (`N`, typically ~40-90), not ploidy scaled near 2-4.
  - The in vitro MAP objective/report path under `code/in-vitro-utils` and `workflow/` now compares observed and predicted mean chromosome count directly on the model `N` scale.
- Current workflow behavior:
  - `sample_invitro_objective_once.R` samples a transformed start point, runs a short local optimization, and appends the optimized result to a shared timestamped TSV.
  - `simulation_basics.Rmd` loads the best available sampled optimization result (defaulting to the newest timestamped TSV when present, otherwise falling back to the committed `invitro_best_parameters.tsv` snapshot), visualizes the resulting single-lineage demo run plus the full multi-lineage objective fit, and includes sampled-start optimizer diagnostics.
  - The report now makes the “top N runs to inspect” configurable, highlights those runs in the objective-value panel, overlays the rank-N fit against the best fit on the growth/karyotype-summary panels, and adds a cheap local `J^T J` identifiability diagnostic around the best recovered parameter set.
- Immediate project goal: treat this as a checkpointed exploratory baseline and use it to decide the next round of objective/data/model refinements.
